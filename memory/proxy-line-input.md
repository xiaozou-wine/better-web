# 代理的一行粘贴，与被拒的标签块格式

2026-07-28 加的功能。表单里原本只有五个独立输入框，而代理商给的是一行文本，用户得手工拆成协议/主机/端口/用户名/密码——拆错顺序或漏掉一段在界面上看不出来。

## 解析必须只有一份实现

一行粘贴走 Wails 绑定 `ParseProxyLine`（`app.go`）转调 `model.ParseProxy`，**没有在前端写 TS 版本**。

理由不是"省事"，是密码含 `@` 或 `:` 时的切法有讲究：`ParseProxy` 对 URL 形式用 `strings.LastIndex(rest, "@")` 而非 `Index`，因为密码里可能含 `@`。前端另写一份迟早在这个用例上分叉，而分叉的后果是表单显示的凭据与实际落库的不是一回事——检测能过、启动却认证失败，且没有任何可见痕迹。

该绑定刻意不调 `a.svc()`，与其余所有绑定的模式相反。解析是纯函数，与数据目录、会话状态都无关，照那个模式写会让它在数据目录不可用时一并失败。`parseproxyline_test.go` 用零值 `App` 锁住这一点。

## 为什么不支持带字段名的多行块

用户问过这种格式，评估后否掉：

```
协议    SOCKS5
主机    198.51.100.10
端口    31800
用户名  xxxx
密码    xxxxx
```

**歧义无解：** 缺「用户名」标签行时，剩下那行是用户名还是密码无法判断。猜错会把密码填进用户名字段，而这类错误在界面上看不出来——两个框都填着东西，看起来正常。

**契约冲突：** `ParseProxyList` 的契约是「一行一个代理」，块解析要求跨行聚合。混在同一个输入框里会让「这段文本到底是几个代理」变得不确定，比如一批四段格式里混进一个中文块。

结论：只支持一行标准格式。这个决定在代码里不会留痕迹，所以记在这。

## 两个实现细节的理由

- **解析成功后清空粘贴框。** 它含密码明文，界面上多留一份就多一个泄漏面；原文留着也没有用处。
- **解析失败不动已填字段。** 一次误粘不该清掉手工填好的配置。

回填后要调 `invalidateCheck()`——代理配置变了，先前的检测结果不再对应当前配置。
