# 回程丢包与 SOCKS5 转发的 deadline 缺陷

2026-07-28 排查。现象：日常模式 `USA` profile（`socks5://198.51.100.10:31800`）访问不了 Google，但同一个代理用 curl 单发是通的。

## 结论：两个独立问题叠加

一是链路——VPS 到本机宽带的**回程方向丢包**，与端口、协议配置无关。二是本项目转发器的 deadline 罩错了范围，被前者放大后必然踩中。

## 根因一：回程丢包（不是代码问题）

在 VPS 上抓 `tcp port 31800`，一次失败的握手长这样：

```
In  [S]   客户端 SYN 到达
Out [S.]  服务器 0.09ms 内回 SYN-ACK
Out [S.]  1s 后重传（客户端未收到）
Out [S.]  2s 后再重传
In  [.]   客户端 ACK 迟到 3.3 秒才到
```

服务器收到了也及时回了，丢的是**回程**的包。服务器侧 `netstat -s` 累计 399851 次重传，吻合。连三次握手都要重传，后续 SOCKS5 协商更容易卡死，一卡就是 21 秒超时。

`danted`（dante SOCKS server）无辜：SYN 到达后 0.09ms 就响应了。

### 为什么现象看着自相矛盾

| 观察 | 原因 |
|---|---|
| 单发能通、连打全崩 | 包一多，丢中关键包的概率接近 1 |
| 静置几分钟又能通 | 运气，不是恢复 |
| 裸 TCP 6/6 通、实际代理 0/6 | 握手只需几个包撑得过；完整会话包多撑不过 |
| 同 VPS 的 hy2 稳定 5/5、ttfb 1.2s | QUIC 有前向纠错，不必等超时重传 |

**hy2 出口 IP 与 SOCKS5 完全相同**（`198.51.100.10`，某 IDC 机房 ASN，美国东部某机房，机房 IP）。同一台机器、同一条回程路径，差别只在传输层。所以走 `socks5://127.0.0.1:10808`（某本地代理客户端的入口）不是绕过问题，它就是这条链路的正解，且延迟只有直连的一半。

### 排障线索

「裸 TCP 通但实际代理不通」= 丢包链路，不是端口封锁。换端口无效——丢的是回程包，与端口号无关。要救得从传输层入手（QUIC/mux 或 BBR），但既然有 hy2 就没必要。

## 根因二：`handle` 的 deadline 罩了两段不同预算的操作

`internal/proxy/socks5.go` 的 `handle` 给本地连接设 `handshakeTimeout`(10s) 的**绝对 deadline**，之后才去做一件预算 `dialTimeout`(20s) 的上游拨号。上游握手耗时落在 10–20s 之间时，隧道其实建好了，但写 SOCKS 应答时 deadline 已过——浏览器只看到一个 `EOF`。

丢包把延迟拉过 10 秒，这个缺陷就必然触发。两个问题会叠加。

修复：拆成三段独立预算。读客户端握手用 `clientHandshakeTimeout`（对端在本机，预算短）；拨上游前**清空**本地 deadline，超时交给 ctx；回应答时重设 `replyTimeout`（防客户端不收时挂死）。

## 为什么原有测试没抓到

`forwarder_test.go` 的伪上游全是零延迟本地 listener，握手在微秒级完成，这个缺陷从未被触发。回归测试 `slowupstream_test.go` 用刻意延迟 12s 的伪上游（落在两个超时之间），两条测试组合起来锁死归因：

1. `TestForwarderSurvivesSlowUpstreamHandshake` — 修复前 FAIL(EOF)，修复后 PASS
2. `TestSlowUpstreamActuallyCompletesHandshake` — 断言上游 `handled > 0`

第 2 条是关键：证明失败发生在「上游已成功、本地已放弃」这个组合上，而不是压根连不上上游。少了它，第 1 条的失败可以被误读成上游不可用。

## 顺带：转发错误原来是静默丢弃的

`serve` 里原本是 `_ = f.handle(conn)`，单条连接的失败全部丢掉。这类故障（代理能用、浏览器打不开）因此无法定位，客户端只看到笼统的 `EOF`。

加了 `Forwarder.OnError` 回调后立刻有回报：排查中一次失败被还原成 `wsarecv: 远程主机强迫关闭`，指向本地代理客户端主动断连而非本项目。**转发失败必须可观测**，否则只能靠猜。

`tunnel` 同样改为返回错误。注意它**刻意只等一个方向**结束：曾改成等两个方向以防数据截断，但那会让 `Close()` 的 `wg.Wait()` 卡在空闲连接上（比原问题更糟），且无证据表明截断真在发生，已回退。

## 排查方法上的教训

前三个判断都被后续实测推翻：

1. 「线路劣化了」→ 静置后单发就通，是自己高频测试打崩的
2. 「31800 被中途阻断」→ 裸 TCP 后来 6/6 通，是间歇性抖动
3. 「danted accept 队列溢出」→ 加压时溢出计数零增长；那 22427 次是历史累积

共同错误是**只在客户端单侧观察**。定案只能靠服务器侧抓包——只有它能同时看到「服务器回了」和「客户端没收到」。另外用 `nc -l` 测端口可达性会给假阴性（单次连接后即退出，表现为 1/3），需要用持续 accept 的监听。

**自己的测试会污染证据：** `cmd/diagproxy` 的 sample 模式默认 8 轮 × 多目标，足以把敏感线路打进限流；本机也一度累积 2919 个 TIME_WAIT（Windows 动态端口池仅 16384）。测敏感线路前先冷却，或降低轮次。
